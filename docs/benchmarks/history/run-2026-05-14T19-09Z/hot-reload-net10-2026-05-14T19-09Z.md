# Hot-reload latency — net10 — 2026-05-14T19-09Z

How long does it take to apply a configuration change to a running
Herald pipeline? This measures the end-to-end `Reload(json)` call —
parse the JSON, detect the diff, apply the new configuration — for
both the fast-path (level-only delta) and slow-path (structural
rebuild).

## What this measures

The bench runs against a pipeline built with `Swappable` + `Async` +
`FanOut` strategy and `WithHotReload()` enabled.

- **FastPath_LevelOnly**: alternate between two JSON configs that
  differ only in minimum level (`debug` vs `warn`). The
  ConfigDiffDetector classifies these as level-only deltas and the
  coordinator updates the live `LogLevelSwitch` in place — no
  pipeline rebuild.
- **SlowPath_NoChange**: reload the same config that's currently
  running. The diff is empty but the coordinator does not fast-path
  no-op deltas; it goes through the full pipeline rebuild path and
  swaps the new (identical) pipeline atomically into the
  `SwappableLogger`. This is the floor cost of a structural rebuild.

## Results

| Method                              | Mean      | Error     | Gen0   | Allocated |
|------------------------------------ |----------:|----------:|-------:|----------:|
| Herald_HotReload_FastPath_LevelOnly | 40.15 μs  | ± 1.97 μs | 0.9155 |  53.79 KB |
| Herald_HotReload_SlowPath_NoChange  | 32.65 μs  | ± 0.64 μs | 0.7324 |  53.79 KB |

## Observations

- **Both paths land in microseconds, not milliseconds.** A
  configuration change applied via `Reload(json)` is human-instant.
  An operator who edits a config file and saves it sees the change
  active within ~40 microseconds — well under the threshold a file
  watcher's debounce window would notice.
- **The 54 KB allocation is JSON parse + runtime-config
  materialization**, not pipeline rebuild. JSON deserialization is
  the dominant cost in both paths; the actual diff-and-apply work is
  a small fraction.
- **Fast-path and slow-path are nearly identical in wall-clock
  time.** Both pay the JSON parse cost; only the slow path rebuilds
  the pipeline graph downstream. The rebuild work fits in the noise
  margin of the parse cost — a few microseconds.
- **In-flight events don't drop.** The slow-path rebuild swaps the
  new pipeline atomically into the SwappableLogger; events emitted
  during the swap complete on the pipeline they entered.

## Why this matters

Most logging libraries treat configuration changes as restart-time
concerns. Serilog has `LoggingLevelSwitch` for atomic level changes;
NLog supports XML config reload via filesystem watching; neither
ships a JSON-driven full-pipeline-swap with zero event loss.

A Herald operator can:

- Change the minimum level live without redeploying.
- Change the sink set live — add a Slack webhook for a 6-hour
  incident, remove it after.
- Switch between profile JSONs (`logging-normal.json` →
  `logging-debug.json`) for incident response.
- Roll back instantly if the new config is wrong; the old config
  is still on disk.

At ~40 μs per reload, the configuration becomes the operational
control plane. That's a different shape of capability than
"restart the service."
