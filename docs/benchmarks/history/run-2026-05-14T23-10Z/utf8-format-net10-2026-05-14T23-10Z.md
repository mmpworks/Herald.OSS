# UTF-8 format end-to-end — net10 — 2026-05-14T23-10Z

End-to-end emit-to-UTF-8-bytes comparison. Each library configured
with its idiomatic "format to bytes then discard" sink.

## Setup

- **Herald**: a bridge sink wrapping `Utf8JsonFormatter` writing to
  a reusable `ArrayBufferWriter<byte>`. The bridge implements
  `ILogger`, not `IKernelSink`, so the chain path runs (full
  `LogEvent` materialization before the formatter).
- **ZLogger**: `AddZLoggerStream(Stream.Null)`. ZLogger's headline
  claim is "UTF-8 from input to output." This is its native path.
- **Serilog**: a custom sink running `CompactJsonFormatter` to a
  `StringWriter` backed by a pooled `StringBuilder`. Serilog
  formats to UTF-16 strings; the rendered text is discarded.

## Honest reading

**Herald loses this comparison.** ZLogger is 4.5× faster and
allocates 20× less; Serilog is 2.8× faster despite going through a
string. The number is what it is.

Why Herald lands here, in plain terms:

1. **The bridge sink forces the chain path.** `HeraldUtf8DiscardSink`
   implements `ILogger`, which means Herald materializes a heap
   `LogEvent` before calling the sink. The chain-path materialization
   is itself ~600+ B; everything else in the 1,448 B is the
   formatter's per-event work.
2. **Herald.OSS does not currently ship a kernel-eligible UTF-8
   sink.** A sink that implements `IKernelSink` and writes through
   `Utf8JsonFormatter` directly from the `LogEventBuffer` would
   skip the chain-path tax entirely. The kernel-fast-path
   accept-call lands at 25–37 ns; adding the JSON-format step on
   top of that should put Herald in ZLogger's neighborhood, not
   1,293 ns away from it.
3. **ZLogger's pipeline is engineered around the UTF-8 byte-pipe
   end-to-end.** Their interpolated string handler emits direct
   `Utf8Formatter` calls; the format work happens during the
   handler, not in a separate sink invocation. Herald's
   architecture splits these into two phases (build buffer, then
   format), and the current shipping path doesn't fuse them.

## What this bench teaches

This is the one row where Herald clearly trails. The result is
worth publishing because:

- **It identifies a real gap.** The kernel-eligible UTF-8 sink is
  follow-up work. Until it ships, adopters who want
  format-to-bytes through Herald should know what it costs.
- **It validates ZLogger's headline.** "UTF-8 from input to
  output" is a real architectural choice that delivers a real win
  on this workload. Honest measurement confirms their claim.
- **It frames what "good" looks like for the follow-up.** Once
  Herald ships a kernel-eligible JSON formatter, the comparison
  re-runs and either matches ZLogger or doesn't. Either result is
  worth publishing.

## Follow-up: kernel-eligible UTF-8 sink

The implementation pattern that should close the gap:

```csharp
public sealed class Utf8JsonKernelSink : ILogger, IKernelSink
{
    private readonly Utf8JsonFormatter _formatter;
    private readonly IBufferWriter<byte> _output;

    public void Log(in LogEventBuffer buffer)
    {
        // Format directly from the stack buffer.
        // No heap LogEvent. No chain path.
        _formatter.FormatFromBuffer(buffer, _output);
    }

    public void Log(LogEvent logEvent) =>
        _formatter.Format(logEvent, _output);  // fallback
}
```

This requires `Utf8JsonFormatter` to grow a
`FormatFromBuffer(in LogEventBuffer, IBufferWriter<byte>)` overload.
Today it only takes `LogEvent`. Once that overload lands, the bench
re-runs without any change to the bench source.
