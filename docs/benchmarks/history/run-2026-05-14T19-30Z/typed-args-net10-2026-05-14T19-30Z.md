# Typed-args accept path: zero-alloc story — net10 — 2026-05-14T19-30Z

Herald's `Info<T1..Tn>` typed-args overloads (1..16 arity, generated
by `TypedArgsOverloadGenerator`) deliver zero-allocation accept-path
emit **when the property values are reference types**. Value-type
properties box at the dispatcher's `object?` boundary. This bench
pins both shapes so the claim is honest: "zero alloc when reference
types are passed" — not "zero alloc, always."

## What this measures

Four shapes. Each calls the typed-args overload generated for the
matching arity. The dispatcher writes the values into a
stack-allocated `LogPropertyCompact` buffer (`InlineArray<N>`) and
forwards to the kernel.

| Shape | Properties | Mix |
|---|---|---|
| FourProps_AllStrings | 4 | all `string` |
| FourProps_MixedTypes | 4 | `string`, `int`, `bool`, `double` |
| SixteenProps_AllStrings | 16 | all `string` |
| SixteenProps_MixedTypes | 16 | 4 each of `string`, `int`, `bool`, `double` |

## Observations

- **All-strings, 16 properties: 37 ns, 0 B.** This is the headline
  number. Sixteen-property accepts that allocate nothing per call,
  in under 40 nanoseconds. No competitor library lands close to
  this shape — published Core numbers put NLog at 918 ns, ZLogger
  at 693 ns, Serilog at 515 ns for the same workload.
- **All-strings, 4 properties: 27 ns, 0 B.** Four-property accept
  in twenty-seven nanoseconds, zero allocation. The dispatch
  baseline is ~25 ns; per-additional-property cost is ~0.7 ns when
  the value is a reference.
- **Per-property scaling is nearly flat for reference types.**
  4 props at 26.6 ns → 16 props at 37.2 ns. Three extra properties
  cost roughly 2 ns total. The InlineArray buffer and span-pass
  through the kernel are doing real work for us.
- **Mixed-type allocations are predictable.** Three boxes at 4
  props = 72 B (one box per non-string value). Twelve boxes at 16
  props = 288 B. The 24 B per box is the standard CLR overhead for
  a boxed primitive in 64-bit.
- **Mixed-type timing scales worse.** 4 props mixed at 36 ns;
  16 props mixed at 83 ns. The 47-ns gap is the boxing cost plus
  Gen0 nursery pressure. Still under any peer library's
  per-call cost for the same shape.

## Why zero-alloc requires reference-type properties

The typed-args dispatcher is:

```csharp
private void DispatchTyped16(
    LogLevel level, LogCategory category, string template,
    object? arg1, ..., object? arg16,
    string? name1, ..., string? name16,
    int filledArity)
{
    var buf = new LogPropertyBuffer16();
    if (filledArity >= 1) buf[0] = new LogPropertyCompact(name1 ?? "arg1", arg1);
    ...
    LogCompact(level, category, template, span);
}
```

The parameters are `object?`. When the caller's `Info<int, ...>`
overload calls this dispatcher with an `int`, the CLR boxes the int
to `object` at the call site. That box is the allocation.

When the caller passes a `string`, no boxing occurs — `string` is
already a reference type, and `object?` stores the reference
directly. Same for any class or record type.

`LogPropertyCompact` itself is a `readonly record struct` with
`Name: string` and `Value: object?`. The struct lives on the stack
(inside the InlineArray buffer); the only heap traffic is the box
(if any) of value-type property values.

## What this means for adopters

- **Identifiers, levels, categories, error codes, names, URLs,
  paths, message texts** — all reference types. Pass them
  directly; zero-alloc.
- **Counters, durations, timestamps, IDs as ints, flags as bools** —
  value types. Each one boxes once per emit.
- **Caller can pre-box value-type properties** by holding `object`-
  typed locals (`object id = userId;`) and passing the local. The
  box happens once at assignment; subsequent emits reuse the
  cached box. Useful in hot loops emitting the same context
  repeatedly.
- **Future work**: a value-typed compact discriminated union
  (tagged struct holding int/long/double/bool/DateTime/string)
  could eliminate boxing for the common primitive types. The
  current shape ships zero-alloc for the common reference-type
  case and one-box-per-primitive for the mixed case.

## Comparison context

Reference numbers from Herald.Core's published competitive bench
(same telescope-exposure workload, 16 properties — competitor rows
not re-run here, Herald-only iteration):

| Library | 16 props mean | Allocated |
|---|---:|---:|
| **Herald typed-args (all-strings)** | **37 ns** | **0 B** |
| MEL (inert NullLogger) | 62 ns | 152 B |
| log4net | 187 ns | 360 B |
| MEL (active provider) | 276 ns | 616 B |
| Serilog | 515 ns | 2 KB |
| ZLogger | 693 ns | 108 B |
| NLog | 918 ns | 3 KB |

Herald's typed-args path is **5× faster** than the next library
(MEL inert NullLogger, which doesn't even invoke the formatter)
and **24× faster** than NLog. The allocation ratio is more
dramatic: every other library allocates per call; Herald allocates
zero for the reference-property case.
