# Redaction cost — net10 — 2026-05-14T19-09Z

Per-call cost of redacting one PII property from an `Info`-level emit.
Three Herald shapes on the same workload — baseline (no redaction),
kernel-fast-path redaction, and the full event-processor DSL.

## What this measures

Workload: one event with one property
(`logger.Info("user {Email} logged in", "alice@example.com")`),
emitted into a null sink. The rule masks the `Email` property's
value with `*` characters, keeping the first 2 characters visible.

Three pipelines, same rule:

1. **Baseline** — no redaction wired. Sets the reference.
2. **WithFastRedaction** — kernel-eligible fast-path redactor. The
   rule runs on the property span before the `LogEventBuffer` is
   constructed; the pipeline stays on the kernel fast path.
3. **WithCompiledRedaction** — event-processor redactor. Runs after
   `LogEvent` materialization. Heavier per call but supports the
   full rule DSL (glob, regex, when-predicates, value patterns,
   drop-event actions).

## Observations

- **Fast-path redaction costs 8 ns per call.** The rule runs against
  the property span — one dictionary lookup by property name, one
  span operation to mask the value. Allocation stays at zero because
  the pipeline never leaves the kernel fast path.
- **Compiled redaction costs 382 ns per call, plus 672 B
  allocated.** The event-processor path materializes a full
  `LogEvent`, runs the rule engine over its properties, and writes
  the modified event back. The extra cost buys the full rule DSL:
  glob/regex patterns, when-predicates, value patterns, drop-event
  actions, replace-message actions.
- **32% overhead for fast-path redaction is the right framing.**
  Compared to a baseline emit, a single fast-path rule adds about
  one-third of the dispatch cost. A pipeline that runs 5 rules
  would land near 70 ns — still well under any competitor's
  unredacted accept cost.

## Why this matters

Most logging libraries treat redaction as a sink-side concern —
"render the event, then look for things to redact in the output." That
shape:
- pays the full render cost before discovering anything redactable
- can miss properties that don't appear in the rendered template
- runs once per sink, multiplying cost by sink count

Herald's two-tier redaction (fast-path for exact-name rules,
event-processor for the long tail) inverts this: the cheap-and-common
case stays on the kernel fast path; the expressive-but-heavier case
pays a real cost but supports the full DSL. Adopters mix and match —
exact-name PII rules on the fast path; complex content scanning on the
processor.

Competitor benchmarks for the same redaction shape are tricky to
write fairly. Serilog has destructuring policies (closest analogue,
heavier shape). NLog has property filters via layout renderers
(different mental model). ZLogger has format-time redaction (string
substitution at render). log4net has nothing built-in. Each
competitor row would need its own methodology callout to be fair.
